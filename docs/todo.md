- [x] **2. 全局「暂停闪避」总开关**（2026-10-22 已实现；验收：暂定通过）
  托盘菜单 + 主界面一键临时停用全部规则；暂停时立即恢复所有被压音量（复用退出还原链路）。现在只能逐条禁用规则或退出程序。典型场景：临时听清被压低的应用、演示。
  > 实现注记：引擎 `SetSuspended`（暂停＝即时还原到原始锚点并清闪避状态；恢复＝以真实音量重起基准）。入口三处同步：托盘菜单勾选项、设置页「启用闪避」开关、顶栏琥珀「闪避已暂停」徽章（仅暂停时出现）。已验证：暂停立即还原、触发持续时恢复会重新闪避。

- [x] **3. 诊断与自查渠道**（原「界面内事件日志」，定位已修正）（2026-10-22 已实现；验收：待后续使用中观察）
  - **定位（审核结论）**：诊断的责任主体是程序和维护人员，不是用户的日常任务；本功能是"提供信心"的自查渠道。**未触发时不占界面**，不能作为核心内容大面积出现。
  - 主动提示（随错误出现，不常驻）：配置未生效时程序主动给出原因，如"规则 N 的触发应用 xxx 未运行 / 名字与实际进程不符（参考：哔哩哔哩）""分组 xx 当前无成员进程在运行"。

## P1 · 规则表达力（产品迭代主线）

- [x] **5. 规则级闪避时长覆盖**（2026-10-22 已实现，待用户验收）
  FadeOut/FadeIn 目前为全局设置；规则加可选时长字段，留空 = 跟随全局，兼容旧配置。场景：视频压音乐快进快出、游戏压慢放慢收。
  > 实现注记：规则页新增「闪避节奏」行（压低/恢复 ms，留空＝跟随全局，50–10000 钳制）；引擎每会话携带当前生效节奏，恢复阶段沿用刚解除规则的覆盖值；锚点保护窗口同步用规则级恢复时长。端到端实测：2500ms 覆盖的压低轨迹 0.5s=88%/1.1s=70%/2.6s=30% 精确线性，恢复同速率回升。

- [x] **6. 规则生效条件**（2026-10-22 已实现，待用户验收；最小版：设备条件）
  如"仅当某输出设备激活时""仅时间段内生效"。最小版本先做一种条件（设备条件最实用：耳机/音箱两套行为）。
  > 实现注记：规则页新增「生效条件」行：无条件 / 指定输出设备（可从枚举设备中选或手输子串，如"耳机"；当前默认设备置顶）。引擎每拍与当前设备名做不区分大小写的子串比对，不满足则该规则本轮不参与；规则列表句尾追加［仅 X］标记。端到端实测：永不匹配的条件使高优先级规则被正确拦截（终值 30% 而非 60%）。时间段条件留待后续按需追加。

- [x] **7. 多规则叠加语义**（2026-10-23 已实现；验收：端到端 7/7，待用户验收）
  同目标多条规则命中时现取优先级最高者；备选"取闪避最深者"（20% 与 40% 同时命中压到 20%）。规则级开关，小改动。
  > 实现注记：实现为**全局设置**「多规则同时命中」（叠加语义决定多条规则之间的合成方式，逐规则各自选语义无法互相合成）：取优先级最高（默认，行为不变）/ 取闪避最深（压到目标音量更低者，并列时仍按优先级决出）。引擎裁决 `Better` 按语义分支；规则页优先级提示同步说明。端到端实测：两条规则 40%(高优) + 20% 同时命中，默认模式终值 40%、deepest 模式终值 20%。

- [x] **8. 手动接管模式**（2026-10-23 已实现；验收：端到端 7/7，待用户验收）
  已知限制第 4 条（闪避期间手动调音量被渐变覆盖，现仅更新恢复目标）。可加选项：用户手动调节即视为接管，该会话本轮闪避不再干预，直到下次触发。
  > 实现注记：设置页「手动调节即接管」开关（默认关，关＝旧行为仅更新恢复锚点）。开启后 `SetUserVolume` 即解除本轮干预（用户值当场生效、引擎不再写该会话），状态页徽章「手动接管（本轮不压低）」、事件日志记接管；规则解除即复位，下次触发恢复闪避。端到端实测：闪避中调节立即生效且不被压回、解除后保持用户值、再触发重新压低、关闭开关时锚点语义不变（恢复到用户调整后的值）。README 已知限制第 4 条描述的是默认关（旧行为）场景，随本功能待下次发版时一并更新。

## 实验性（先探针验证，再决定立项）

- [x] **14. 「暂停目标应用」作为闪避替代动作**（探针已完成 2026-10-23；**是否立项待用户决定**）
  看视频时直接暂停音乐播放器（而非压音量），视频停了自动恢复播放。第三方经 SMTC 请求暂停支持有限，大概率需向目标应用发送媒体键，可靠性存疑——先做可行性探针，再决定。
  > 探针结论（2026-10-23 两轮实测）：**SMTC 真启停可行，含真实第三方播放器**。①WinRT MediaPlayer 音源：TryPause 后峰值连续归零、状态=已暂停、TryPlay 恢复；②**QQ音乐实测**（Tuner 典型目标应用，自带 SMTCFeature.dll）：TryPlay=True 后真实出声（峰值 28-31%），TryPause=True 后声音真停（峰值 4s 归零保持、状态=已暂停）——"第三方支持有限"的担忧在 QQ音乐上不成立。B站/网易云等按需复测（工具就绪：`PauseProbe list` / `PauseProbe test <关键字>`）。边界：对未注册 SMTC 的应用（部分游戏/老播放器）完全无效，若立项需回退压音量路径。**技术可行性已验证，是否立项由用户决定。**

## 长期方向（单独立项评估，不排入常规迭代）

- [ ] **15. 多端适配（macOS / Linux）**（Linux 已打通原型 2026-10-23；macOS 评估完成待决策）
  目标：不能只用于 Windows。
  现实约束：音频层 WASAPI（NAudio）为 Windows 专属——macOS 需 CoreAudio、Linux 需 PipeWire/PulseAudio，会话监控与音量控制层需按平台整体重写；UI 层 WPF 同为 Windows 专属，需换跨平台框架（如 Avalonia）或分平台实现。Tuner.Core 中规则引擎、配置、音量曲线等 UI 无关部分可直接复用。工程量约等于按平台重做核心层，需单独立项评估。
  > **推进注记（2026-10-23/24，四步全部推进）**：
  > ① **Core 平台抽象**（完成）：Tuner.Core 拆纯跨平台 net8.0（引擎/配置/曲线 + `IAudioSessionMonitor`/`IMediaSessionTracker` 接口），Windows 实现收敛到新工程 Tuner.Core.Windows（WASAPI/SMTC），命名空间不变引用方零改动；引擎改接口注入。
  > ② **Linux 平台层**（完成，WSLg 实测）：Tuner.Core.Linux（P/Invoke libpulse）——sink_input 会话枚举/进程名/PID/corked 状态/音量读写/主音量/设备枚举全部端到端验证。**边界**：PulseAudio 无 per-stream 峰值（sound 判定不可用，state 判定用 corked）；MPRIS 媒体状态未接。
  > ③ **Avalonia 跨平台 UI**（完成 v1，Windows/WSLg 双端冒烟通过）：Tuner.App.Avalonia 单源码双目标（net8.0-windows→WASAPI、net8.0→PulseAudio），五页功能完整 + 双语即时切换 + 托盘 + 导入导出 + 更新检查 + 诊断日志。**已知差距（后续迭代）**：动效精细度（滑动胶囊/分层渐变）、推子回写博弈完整版、自定义曲线点编辑、滚轮调音、开机自启、全局热键。跨平台制品暂未入 dist（Windows 四件套纪律不含 Avalonia，打包形态与分发范围待决策）。
  > ④ **macOS**（骨架+蓝图，需 Mac 接手）：Tuner.Core.macOS 公开 API 设备级实现（编译通过未运行验证）；完整 per-app 能力需虚拟音频驱动路线（AudioDriverKit，可借鉴 MIT 的 BackgroundMusic）+ Apple 开发者签名——方案与工程量见 docs/macOS-plan.md。**公开 API 范围内 per-app 不可行的结论不变。**
